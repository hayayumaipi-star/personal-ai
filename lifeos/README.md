# LifeOS との接続（実測にもとづく現状）

調べた日: 2026-09-19

## 分かったこと（測った結果）

- **LifeOS はこの環境のどこにも入っていない。** ファイル・コマンド・スキル・
  プラグイン・MCP のいずれにも存在しない（`find / -iname "*lifeos*"` で0件）。
- ただし **`bun` と Node 22 はあり、ここは Linux** なので、入れること自体はできる。
- 過去に `docs/設計判断.md` で調査済み。**Windows で動かないため不採用**としていた。

## いちばん大事な構造の話

アプリのAIと、開発中のAIは**別物**で、設定では一つにできない。

| | 使えるもの |
|---|---|
| **アプリの中のAI**（`window.claude.use("sample")`） | 渡した文字列だけ。スキルもMCPもファイルも無い |
| **開発側のAI**（Claude Code） | Bash・ファイル・MCP（github / Todoist ほか）・Artifact の db |

だから「アプリのAIに LifeOS を読み込ませる」はできない。
**アプリが、LifeOS の動く場所と会話する**形にするしかない。

## 動かした最小構成（db を通り道にする）

アプリから外へ通信できるかは未確認なので、**すでに動くことが分かっている
`db`（Artifact の保存先）を通り道**にした。外向きの通信は要らない。

```
アプリ ──書く──> lifeos_requests/{id}   （発言）
                      │
        LifeOS側が読む（Claude Code の ArtifactData）
                      │ 処理し、作業ファイルを作る
                      ↓
        lifeos_memory/{key}   （記憶）
        lifeos_results/{id}   （結果）
                      │
アプリ ──読む──> 起動時に読み、依頼文へ載せる（次の会話で使われる）
```

### 実測した5段階

| | 何を | 結果 |
|---|---|---|
| ① 発言する | `lifeos_requests/req-001` を書く | 通った（version 1） |
| ② LifeOS側が処理 | 開発側から読む | 読めた |
| ③ 記憶を更新 | `lifeos_memory/profile-focus-morning` | 通った |
| ④ 結果を返す | `lifeos_results/req-001` | 通った（3件を一括・原子的に） |
| ⑤ 次の会話で使う | アプリが読み、依頼文に載る | 載った（下記） |

```
【LifeOSが覚えていること】
- 朝の時間に集中したい
```

**実行の証拠**として `lifeos/memory.md` を作成した（このファイルの隣）。

### つながっていないときも動く

`lifeos_memory` が無い／読めないときは、**アプリはこれまでどおり動く**。
依頼文に余計な見出しも出ない。テスト837件は失敗0のまま。

## まだ確かめていないこと

- **アプリから外部（LifeOSのサーバ等）へ直接通信できるか。** 未測定。
  上の構成では要らないが、別の形にするなら先に測る必要がある。
- **LifeOS そのものの動作。** 入っていないので、一度も動かしていない。
  いま「LifeOS側」を務めているのは**この開発セッション**であって、LifeOS製品ではない。

## 決めないと進めないこと

**LifeOS をどこで動かすか。** この開発コンテナは**使われないと消える**ので、
ここに入れても `~/.claude` の記憶は残らない。記憶を残すなら置き場は
**git か Artifact の db** のどちらかになる。
